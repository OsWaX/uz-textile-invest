## 1. Общие сведения

### 1.1. Наименование системы

Полное наименование: **Торговая интернет-площадка (маркетплейс) прямых продаж
без складов оператора**. Условное обозначение в документе — «Платформа».

### 1.2. Назначение

Платформа — двусторонняя электронная торговая площадка, соединяющая продавцов
(юридические лица, индивидуальные предприниматели, самозанятые, ремесленники,
фермерские хозяйства) с покупателями — физическими и юридическими лицами.

Платформа **не является собственником товара**, не хранит товар и не выступает
стороной договора купли-продажи. Договор заключается напрямую между продавцом
и покупателем; Платформа оказывает услуги информационного посредничества,
организации расчётов и разрешения споров.

### 1.3. Основание для разработки

Анализ сильных и слабых сторон действующих площадок (Amazon, Wildberries, Ozon,
Uzum Market, eBay, Etsy, Temu), изложенный в [research.md](research.md), и
структурные особенности рынка Узбекистана: доля электронной коммерции в рознице
около 2,2 % при среднегодовом росте около 40 %, концентрация складской
инфраструктуры в Ташкенте, слабая логистическая связность регионов.

### 1.4. Отличие от существующих площадок

| Признак | Классический маркетплейс | Платформа |
|---|---|---|
| Где физически находится товар | На складе оператора | Всегда у продавца |
| Кто отгружает | Оператор | Продавец сам или выбранная им курьерская служба |
| Куда поступают деньги покупателя | На счёт оператора, затем частями продавцу | Расщепляются в момент оплаты: доля продавца — на его расчётный счёт |
| Срок получения денег продавцом | 2–4 недели, ускорение платное | До 24 часов после подтверждения получения товара; для проверенных продавцов — в момент оплаты |
| Структура сборов | Комиссия + логистика + хранение + подписка + реклама | Одна комиссия за состоявшуюся сделку; остальное — добровольные сервисы |
| Изменение тарифов | В одностороннем порядке, иногда задним числом | Не ранее чем через 60 календарных дней, без обратной силы |
| Собственные продажи оператора | Есть (1P, СТМ) | Запрещены уставом и настройками системы |

### 1.5. Участники

| Участник | Роль |
|---|---|
| Оператор Платформы | Юридическое лицо — резидент Республики Узбекистан; владеет Платформой, ведёт реестр продавцов, разрешает споры |
| Продавец | Зарегистрированный субъект предпринимательства, размещает товары, хранит их у себя, отгружает и несёт ответственность за качество |
| Покупатель | Физическое или юридическое лицо |
| Платёжная организация / банк-эквайер | Обеспечивает приём платежей и расщепление сумм между продавцом и Оператором |
| Курьерские службы | Подключённые перевозчики, оказывающие услугу доставки продавцу по договору |
| Государственные информационные системы | ОФД (фискализация), ЭСФ, реестр субъектов электронной коммерции, OneID |

### 1.6. Термины и сокращения

| Термин | Значение |
|---|---|
| **Расщепление платежа (split payment)** | Операция, при которой сумма платежа покупателя в момент проведения делится эквайером на доли: сумма продавца зачисляется на его банковский счёт, комиссия — на счёт Оператора |
| **Защищённый режим (hold)** | Режим, при котором доля продавца резервируется эквайером до подтверждения получения товара и раскрывается автоматически |
| **SLA отгрузки** | Обязательный срок передачи заказа перевозчику, установленный для продавца |
| **Оферта** | Публичный договор Оператора с продавцом; хранится в системе версионно |
| **Спор** | Формализованная состязательная процедура рассмотрения претензии по заказу |
| **Витрина** | Публичная часть Платформы для покупателей |
| **Кабинет продавца** | Закрытая часть Платформы для продавца |
| **ОФД** | Оператор фискальных данных |
| **ЭСФ** | Электронный счёт-фактура |
| **DBS** | Delivery by Seller — доставка силами продавца |

## 2. Цели, задачи и показатели успеха

### 2.1. Цели

1. Дать продавцу канал продаж, не требующий ни складских поставок, ни
   оборотного капитала, замороженного в выплатах.
2. Дать покупателю уровень защиты, не уступающий складским маркетплейсам,
   без владения товаром со стороны Оператора.
3. Вовлечь в электронную торговлю региональных производителей и ремесленников,
   для которых поставка на столичный склад экономически бессмысленна.

### 2.2. Задачи первой очереди (MVP)

1. Регистрация и верификация продавца с проверкой по государственным реестрам.
2. Каталог, карточка товара, поиск и фильтрация.
3. Корзина с разделением заказа по продавцам, оформление заказа.
4. Оплата с расщеплением суммы между продавцом и Оператором.
5. Подключение курьерских служб и самовывоза, трекинг.
6. Возвраты и споры.
7. Отзывы по подтверждённым покупкам.
8. Кабинет продавца и административная панель Оператора.

### 2.3. Показатели успеха

| Показатель | Целевое значение | Способ измерения |
|---|---|---|
| Срок поступления денег продавцу | ≤ 24 ч после подтверждения получения; ≤ 1 мин при мгновенном расщеплении | Отчёт по выплатам |
| Совокупная нагрузка на продавца | ≤ 12 % от суммы заказа (комиссия и обязательные сборы) | Финансовый отчёт |
| Доля заказов, отгруженных в SLA | ≥ 95 % | Логистический отчёт |
| Доля заказов со спором | ≤ 1,5 % | Реестр споров |
| Срок рассмотрения спора | ≤ 5 рабочих дней, медиана ≤ 2 дней | Реестр споров |
| Доля продавцов не из Ташкента | ≥ 40 % к концу 12-го месяца | Реестр продавцов |
| Время ответа витрины (p95) | ≤ 400 мс | APM-мониторинг |
| Доступность | ≥ 99,5 % в месяц | Мониторинг |

## 3. Принципы платформы

Принципы носят обязательный характер: они закрепляются не только в договорах,
но и в логике системы. Изменение любого принципа требует изменения настоящего ТЗ.

**П1. У Оператора нет складов.** В системе отсутствуют сущности «склад
оператора», «поставка на склад», «приёмка», «хранение». Остаток товара
ведётся по складам продавца.

**П2. Деньги покупателя идут продавцу напрямую.** Сумма расщепляется на
стороне эквайера. Оператор не аккумулирует выручку продавцов на своих счетах
и не выступает их держателем.

**П3. Одна комиссия.** Никаких сборов за хранение, приёмку, «сервисное
обслуживание», обязательную рекламу и вывод собственных денег.

**П4. Тариф не меняется задним числом.** Новая версия тарифа вступает в силу
не ранее чем через 60 календарных дней с даты публикации и не применяется к
заказам, принятым до этой даты. Все версии оферты и тарифов доступны в
кабинете продавца.

**П5. Каждое удержание обосновано.** Любое списание с продавца содержит
ссылку на пункт правил, описание события, доказательство и кнопку апелляции.

**П6. Оператор не торгует.** У Оператора и аффилированных с ним лиц не может
быть учётной записи продавца. Ограничение реализуется проверкой ИНН при
регистрации.

**П7. Ранжирование объяснимо.** Формула ранжирования публикуется. Рекламные
позиции занимают не более 20 % выдачи на экран, помечены контрастной плашкой
«Реклама» и не смешиваются с органическими карточками визуально.

**П8. Отзыв нельзя купить и нельзя удалить.** Отзыв оставляется только по
доставленному заказу. Оператор не удаляет отзывы по просьбе продавца;
модерация возможна только по опубликованному перечню оснований, с публикацией
факта модерации.

**П9. Спор состязателен.** Обе стороны представляют доказательства в
регламентированный срок, решение мотивировано и содержит ссылку на правило.

**П10. Данные продавца принадлежат продавцу.** Выгрузка полного набора данных
(товары, заказы, покупатели по своим заказам, финансы) доступна в машинном
формате в любой момент, без обращения в поддержку.

## 4. Роли и права доступа

### 4.1. Перечень ролей

| Роль | Носитель | Назначение |
|---|---|---|
| Гость | Не авторизован | Просмотр каталога, поиск |
| Покупатель | Физическое лицо | Заказы, отзывы, споры, возвраты |
| Корпоративный покупатель | Юридическое лицо | То же + счета, ЭСФ, отсрочка по договору |
| Владелец магазина | Продавец | Полный доступ к своему магазину, финансовые реквизиты |
| Менеджер магазина | Сотрудник продавца | Товары, заказы; без доступа к реквизитам и выводу |
| Кладовщик магазина | Сотрудник продавца | Только сборка и отгрузка заказов |
| Модератор | Оператор | Проверка карточек, отзывов, жалоб |
| Арбитр | Оператор | Рассмотрение споров, решения по возвратам |
| Финансовый оператор | Оператор | Сверка расщеплений, компенсации, отчётность |
| Служба поддержки | Оператор | Просмотр заказов и переписки, без изменения финансов |
| Администратор | Оператор | Настройки, тарифы, справочники, пользователи |
| Аудитор | Оператор / внешний | Только чтение, включая журнал аудита |

### 4.2. Требования к разграничению доступа

1. Модель — RBAC с проверкой принадлежности объекта магазину (multi-tenant
   изоляция): продавец не может получить данные чужого магазина ни через
   интерфейс, ни через API, ни подбором идентификаторов.
2. Все действия ролей Оператора фиксируются в неизменяемом журнале аудита
   (кто, что, когда, прежнее и новое значение, IP).
3. Доступ к персональным данным покупателя для продавца ограничен объёмом,
   необходимым для доставки, и только по активным заказам; после закрытия
   заказа контактные данные маскируются.
4. Двухфакторная аутентификация обязательна для всех ролей Оператора и для
   роли «Владелец магазина».

## 5. Бизнес-модель и тарифная политика

### 5.1. Источники дохода Оператора

| Источник | Характер | Ставка (ориентир) |
|---|---|---|
| Комиссия за состоявшуюся сделку | Обязательный | 3–8 % в зависимости от категории; предельная ставка фиксируется офертой |
| Продвижение в выдаче | Добровольный | Аукцион CPC, лимит доли рекламных мест |
| Расширенная витрина магазина (брендированная страница, домен) | Добровольный | Подписка |
| Услуги проверки и сертификации продавца («Проверенный продавец») | Добровольный | Разовый платёж |
| Кредитные и страховые продукты партнёров | Добровольный | Партнёрское вознаграждение |

### 5.2. Что Оператор не взимает

Хранение, приёмку, «услугу вывода средств», обязательное участие в акциях,
комиссию за отменённый или невыкупленный заказ (кроме фактических расходов
перевозчика, подтверждённых документом).

### 5.3. Правила изменения тарифов

1. Каждый тариф имеет версию, дату публикации и дату вступления в силу.
2. Минимальный срок между публикацией и вступлением в силу — 60 календарных дней.
3. К заказу применяется версия тарифа, действовавшая на момент его создания;
   версия сохраняется в заказе как неизменяемое значение.
4. Кабинет продавца показывает сравнение действующей и будущей версий.
5. Уведомление о новой версии направляется всем продавцам (почта, кабинет,
   Telegram) в день публикации.

### 5.4. Калькулятор

До публикации товара продавец видит расчёт: цена → комиссия → эквайринг →
предполагаемая стоимость доставки → сумма к получению. Тот же расчёт
показывается в карточке заказа фактическими значениями.

## 6. Финансовый контур: платежи и прямые выплаты продавцу

Это ключевой раздел, отличающий Платформу от существующих площадок.

### 6.1. Общая схема

```
Покупатель
   │  оплата картой / QR / рассрочка
   ▼
Платёжная организация (эквайер) ── расщепление в момент проведения платежа
   ├──────────────► расчётный счёт ПРОДАВЦА          (сумма товара и доставки продавца)
   ├──────────────► счёт ОПЕРАТОРА                    (комиссия)
   └──────────────► счёт ПЕРЕВОЗЧИКА (при выборе)     (стоимость доставки)
```

Оператор не является получателем выручки продавца ни на каком этапе. Через
счета Оператора проходит только его собственная комиссия.

### 6.2. Режимы расчёта

| Режим | Кому доступен | Момент зачисления продавцу | Назначение |
|---|---|---|---|
| **Мгновенное расщепление** | Проверенным продавцам с рейтингом ≥ 4,6 и долей споров ≤ 1 % за 90 дней | В момент проведения платежа | Максимальная скорость денег |
| **Защищённый режим (по умолчанию)** | Всем | Автоматически в течение 24 ч после подтверждения получения товара либо по истечении срока автоподтверждения | Защита покупателя |
| **Оплата при получении** | По решению продавца для своих товаров | После инкассации перевозчиком и расщепления входящего платежа | Регионы с низким проникновением карт |

Автоподтверждение получения наступает через 72 часа после статуса «Доставлено»
от перевозчика, если покупатель не заявил претензию.

### 6.3. Требования к платёжному провайдеру

1. Провайдер — лицензированная платёжная организация или банк Республики
   Узбекистан, поддерживающая расщепление платежа и субсчета мерчантов.
2. Поддержка: Uzcard, Humo, Visa, Mastercard, UzQR, платёжные приложения
   (Payme, Click, Uzum Bank), рассрочка партнёрских банков.
3. Обязательные операции API: авторизация, подтверждение, частичная и полная
   отмена, частичный и полный возврат, расщепление, статус, реестр операций.
4. Идемпотентность всех финансовых операций по ключу `idempotency_key`.
5. Ежедневный машиночитаемый реестр операций для автоматической сверки.
6. Хранение платёжных данных на стороне провайдера; Платформа не хранит
   номера карт (PCI DSS SAQ-A).

### 6.4. Возвраты

1. Возврат инициируется из карточки заказа покупателем либо решением арбитра.
2. Возврат исполняется тем же платёжным методом, что и оплата.
3. При возврате комиссия Оператора возвращается продавцу пропорционально
   возвращённой сумме — Оператор не зарабатывает на несостоявшейся сделке.
4. Если средства уже зачислены продавцу (мгновенный режим), возврат
   производится: (а) из последующих поступлений продавца, (б) из
   обеспечительного депозита продавца, (в) при недостаточности — прямым
   требованием к продавцу с блокировкой публикации новых товаров.
5. Обеспечительный депозит для режима мгновенного расщепления — величина,
   рассчитываемая как средний недельный объём возвратов продавца × 2,
   но не менее установленного минимума.

### 6.5. Фискализация и налоговый учёт

1. Продавец является продавцом по договору, следовательно фискальный чек
   формируется от его имени. Платформа поддерживает два варианта:
   - интеграция кассового решения продавца (передача заказа в его онлайн-кассу);
   - выдача чека через ОФД-провайдера Платформы по поручению продавца,
     с указанием продавца в чеке.
2. Для корпоративных покупателей формируется ЭСФ от имени продавца.
3. Платформа передаёт продавцу и в его учётную систему полный реестр операций
   (продажи, комиссии, возвраты) для налогового учёта.
4. Расчёты ведутся через выделенные банковские счета участников электронной
   коммерции в соответствии с правилами электронной коммерции.

### 6.6. Финансовая прозрачность в кабинете

Для каждого заказа отображается: сумма покупателя, комиссия Оператора со
ссылкой на версию тарифа, эквайринговая комиссия, стоимость доставки,
удержания (при наличии, с обоснованием), сумма, зачисленная продавцу, дата и
идентификатор платёжной операции. Выгрузка — CSV, XLSX, JSON, а также через API.

## 7. Логистика без складов оператора

### 7.1. Модели доставки

| Код | Модель | Кто везёт | Применение |
|---|---|---|---|
| **SDS** | Seller Direct Shipping | Курьер продавца | Город продавца, крупногабарит, скоропортящийся товар |
| **CRS** | Carrier Selected by Seller | Подключённая курьерская служба, заказ создаётся из кабинета в один клик | Основная модель для межрегиональной доставки |
| **PSU** | Pickup at Seller | Самовывоз покупателем у продавца | Локальные продажи, крупногабарит, примерка |
| **PUP** | Pickup Point | Пункт выдачи партнёра (не Оператора) | Города, где партнёр имеет сеть |
| **POST** | Почтовая отправка | Почта Узбекистана | Отдалённые районы |

Оператор не владеет ни транспортом, ни пунктами выдачи; все точки в модели
PUP принадлежат партнёрам и подключаются по договору.

### 7.2. Требования к логистическому модулю

1. **Единое окно перевозчиков.** При сборке заказа продавец видит список
   доступных перевозчиков со сроком, стоимостью и рейтингом; выбор — один клик,
   накладная и штрихкод формируются автоматически.
2. **Расчёт стоимости до оформления.** Покупатель на этапе корзины видит
   стоимость и срок доставки по своему адресу от каждого продавца отдельно.
3. **Мультипродавцовый заказ.** Заказ из товаров нескольких продавцов
   разбивается на отправления; каждое имеет свой статус, свою накладную и свой
   расчёт.
4. **Единый трекинг.** Статусы перевозчиков нормализуются к единой модели
   статусов Платформы (приложение 19.2) и показываются покупателю в одной ленте.
5. **SLA отгрузки.** Продавец обязан передать заказ перевозчику в течение
   установленного срока (по умолчанию — до 18:00 следующего рабочего дня).
   Нарушение фиксируется автоматически и влияет на рейтинг и на позицию в
   выдаче; ручные штрафы не применяются.
6. **Фиксация вложения.** При сборке продавец обязан приложить фотографию или
   короткое видео упакованного заказа со считываемым номером отправления.
   Материал хранится 90 дней и является доказательством в споре.
7. **Зоны доставки.** Продавец задаёт зоны (город, область, вся страна) и
   правила бесплатной доставки от суммы.
8. **Отмена и невыкуп.** Возвратное движение товара оплачивается по
   фактическому тарифу перевозчика, документально подтверждённому; Платформа
   не начисляет собственных сборов за отмену.

### 7.3. Требования к подключению перевозчика

Перевозчик подключается через типовой адаптер, реализующий: расчёт тарифа,
создание отправления, получение печатной формы, отслеживание статуса,
подтверждение вручения, отмену, возврат. Адаптер работает по вебхукам; при их
отсутствии — по опросу не реже одного раза в 15 минут. Добавление нового
перевозчика не должно требовать изменения ядра — только реализации адаптера.

## 8. Функциональные требования

### 8.1. Регистрация и верификация продавца

1. Регистрация по номеру телефона с подтверждением по SMS и через OneID (для
   субъектов предпринимательства).
2. Обязательные сведения: ИНН/ПИНФЛ, наименование, форма собственности,
   юридический и фактический адреса, банковские реквизиты (расчётный счёт для
   расщепления), контактное лицо, категория товаров.
3. **Автоматическая проверка** по государственным реестрам: действующая
   регистрация, отсутствие в перечне ликвидированных, соответствие видов
   деятельности, совпадение владельца счёта и ИНН.
4. Проверка на аффилированность с Оператором (принцип П6) — отказ в регистрации.
5. Ручная модерация первых пяти карточек товара нового продавца.
6. Статусы продавца: `draft` → `pending` → `active` → `limited` → `suspended` →
   `terminated`. Каждый переход мотивирован и уведомляется.
7. Значок «Проверенный продавец» присваивается после: 30 дней работы,
   50 выполненных заказов, доли споров ≤ 1 %, отсутствия нарушений SLA свыше 5 %.
8. Срок рассмотрения заявки — не более 2 рабочих дней; отказ — с указанием
   причины и порядка повторной подачи.

### 8.2. Каталог, карточка товара, контент

1. **Категории** — иерархический классификатор (не менее 4 уровней) с
   набором атрибутов на категорию. Управляется Администратором, версионируется.
2. **Карточка товара** содержит: наименование, бренд, категорию, атрибуты,
   описание, фотографии (не менее 3, до 15), видео, габариты и вес (обязательно
   — от них зависит расчёт доставки), состав/материал, страну производства,
   гарантию, срок годности, сертификаты, штрихкод (при наличии).
3. **Варианты (SKU)** — размер, цвет, комплектация; остаток и цена задаются на
   уровне SKU.
4. **Карточка принадлежит продавцу.** Единая обезличенная карточка на всех
   продавцов **не применяется**: покупатель всегда видит, чей это товар.
   Для одинаковых товаров разных продавцов формируется блок «Тот же товар у
   других продавцов» с явным перечнем продавцов, цен и сроков.
5. **Локализация контента.** Обязательные поля заполняются минимум на одном
   языке; автоматический перевод предлагается, но помечается как машинный.
6. **Модерация** карточек — по опубликованному чек-листу; отказ содержит
   конкретный пункт и пример исправления.
7. **Запрещённые товары** — справочник, поддерживаемый Администратором;
   автоматическая проверка по ключевым словам и изображениям с ручной проверкой.
8. **Массовые операции**: импорт и экспорт XLSX/CSV, импорт по YML/XML-фиду,
   синхронизация через API с 1С, «МойСклад» и подобными системами.

### 8.3. Поиск, ранжирование и реклама

1. Поисковый движок с поддержкой узбекского (латиница и кириллица), русского
   и английского языков, морфологии, опечаток, транслитерации и синонимов.
2. Фильтры: категория, цена, атрибуты, продавец, регион продавца, срок
   доставки в адрес покупателя, рейтинг, наличие.
3. **Опубликованная формула ранжирования.** Ранжирование определяется:
   релевантностью запросу, сроком доставки до конкретного покупателя,
   рейтингом продавца, долей выполненных в SLA заказов, ценой с учётом
   доставки, конверсией карточки. Вес каждого фактора публикуется в
   справочном разделе; изменение весов публикуется за 30 дней.
4. **Не влияют на органическое ранжирование**: рекламный бюджет, участие в
   акциях Оператора, использование платных сервисов.
5. **Реклама**: отдельные позиции, не более 20 % позиций на экране,
   контрастная плашка «Реклама», исключена из блока «лучшее предложение».
6. Ранжирование по региону: при прочих равных выше показывается продавец,
   способный доставить быстрее в адрес покупателя, что автоматически
   поддерживает региональных продавцов.
7. Персональные рекомендации на главной и в карточке; пользователь может
   отключить персонализацию.

### 8.4. Корзина и оформление заказа

1. Корзина группирует товары по продавцам; для каждой группы — свои условия
   доставки, срок и минимальная сумма.
2. Заказ создаётся как один платёж покупателя и **несколько отправлений**
   (по числу продавцов), каждое со своим расчётом и своим расщеплением.
3. Оформление доступно без регистрации по номеру телефона (гостевой заказ),
   с последующим созданием учётной записи.
4. Адрес: выбор из справочника адресов, карта, определение по геолокации,
   поддержка адресов без формальной нумерации (ориентиры) — существенно для
   регионов.
5. Перед оплатой покупателю показывается итог по каждому продавцу: товар,
   доставка, срок, продавец, условия возврата.
6. Заказ фиксирует неизменяемые значения: версия оферты, версия тарифа,
   цена, скидка, стоимость доставки, реквизиты расщепления.

### 8.5. Оплата

1. Методы: карта (Uzcard, Humo, Visa, Mastercard), QR (UzQR), платёжные
   приложения, рассрочка партнёрских банков, оплата при получении, для
   юридических лиц — счёт и перечисление.
2. Расщепление и режимы — по разделу 6.
3. Ошибки оплаты обрабатываются идемпотентно, повторная попытка не создаёт
   второй заказ.
4. Для рассрочки: расщепление производится банком-партнёром, продавец получает
   полную сумму независимо от графика платежей покупателя.

### 8.6. Управление заказом и доставка

1. Статусная модель заказа и отправления — приложение 19.2.
2. Продавец получает уведомление о заказе (кабинет, Telegram, SMS, push) и
   обязан подтвердить его в течение 2 часов в рабочее время.
3. Сборка: печать накладной, фиксация вложения (п. 7.2.6), передача перевозчику.
4. Покупатель видит единую ленту статусов по каждому отправлению.
5. Изменение состава заказа после оплаты запрещено; допускается частичная
   отмена позиции с частичным возвратом.

### 8.7. Возвраты и споры

1. **Право на возврат** товара надлежащего качества — в срок, установленный
   законодательством о защите прав потребителей, с сохранением товарного вида.
2. **Претензия по качеству** подаётся из карточки заказа с обязательным
   приложением фотографий или видео.
3. **Состязательная процедура:**
   - шаг 1 — прямое урегулирование: продавец отвечает в течение 48 часов;
   - шаг 2 — при недостижении согласия спор передаётся арбитру Оператора;
     стороны представляют доказательства в течение 72 часов;
   - шаг 3 — решение арбитра: мотивированное, со ссылкой на пункт правил,
     публикуется обеим сторонам; срок — не более 5 рабочих дней;
   - шаг 4 — апелляция в течение 5 дней, рассматривается другим арбитром.
4. Доказательства продавца (фиксация вложения, трек, переписка) и покупателя
   (фото, видео, акт перевозчика) хранятся в деле спора.
5. Решение исполняется автоматически: возврат средств, компенсация,
   отклонение претензии.
6. **Статистика споров публикуется**: доля решений в пользу покупателя и
   продавца по кварталам — как гарантия непредвзятости Оператора.
7. Признаки потребительского фрода (серийные возвраты, подмена вложения)
   фиксируются в профиле покупателя и учитываются при рассмотрении.

### 8.8. Отзывы, рейтинги и репутация

1. Отзыв доступен только по заказу в статусе «Доставлен», в течение 60 дней.
2. Отзыв содержит оценку (1–5), текст, до 10 фотографий, видео; отдельно —
   оценка товара и оценка обслуживания продавца.
3. Продавец отвечает на отзыв публично; удалять отзывы не может.
4. Оператор удаляет отзыв только по опубликованным основаниям (нецензурная
   лексика, персональные данные, реклама, не относится к товару), с указанием
   основания и сохранением факта удаления в журнале.
5. **Рейтинг продавца** — агрегат: оценка обслуживания (40 %), доля отгрузок
   в SLA (30 %), доля споров, решённых не в его пользу (20 %), скорость ответа
   покупателю (10 %). Формула публикуется, значения — в кабинете продавца.
6. Покупка отзывов и накрутка: автоматическое выявление аномалий (всплески
   оценок, повторяющиеся устройства, тексты-шаблоны), проверка модератором,
   санкции по опубликованной шкале.

### 8.9. Коммуникации

1. Внутренний чат «покупатель — продавец» по заказу с сохранением истории и
   маскированием персональных данных.
2. Уведомления: push (мобильное приложение), Telegram-бот, SMS, электронная почта.
   Пользователь настраивает каналы; транзакционные уведомления отключить нельзя.
3. Чат «продавец — поддержка Оператора» с номером обращения и SLA ответа.
4. Шаблоны сообщений на трёх языках.

### 8.10. Кабинет продавца

Разделы: панель показателей, товары, заказы, отправления, финансы, споры,
отзывы и рейтинг, продвижение, настройки магазина и зон доставки, сотрудники
и права, документы и оферты, API-ключи, выгрузки.

Обязательные возможности:
- панель «деньги»: поступило сегодня, ожидает раскрытия, удержано (с причиной);
- калькулятор цены и комиссии (п. 5.4);
- журнал всех действий и всех начислений с фильтрами и экспортом;
- полная выгрузка данных магазина (принцип П10) одной операцией;
- мобильная версия кабинета для приёма и сборки заказов со смартфона —
  обязательное требование: значительная часть продавцов работает без компьютера.

### 8.11. Административная панель Оператора

Разделы: продавцы и верификация, модерация карточек, категории и атрибуты,
запрещённые товары, споры, финансы и сверка, тарифы и версии оферт,
перевозчики, промо и баннеры, пользователи и роли, справочники регионов,
журнал аудита, отчёты, системные настройки, управление контентом справки.

Обязательные ограничения: невозможность создания учётной записи продавца,
аффилированной с Оператором; невозможность изменения отзыва; невозможность
изменения финансового документа задним числом (только сторнирующая запись).

### 8.12. Кабинет покупателя

Заказы и отправления, трекинг, возвраты и споры, избранное, списки,
сохранённые адреса, способы оплаты, отзывы, подписки на снижение цены,
настройки уведомлений, удаление учётной записи и выгрузка своих данных.

### 8.13. Промо и маркетинг

1. Скидки и акции создаёт **продавец**; участие в акциях Оператора —
   добровольное, отказ не влияет на органическое ранжирование (принцип П7).
2. Промокоды: продавца (за его счёт) и Оператора (за счёт Оператора,
   компенсация продавцу в полном объёме).
3. Реферальная программа, бонусные баллы за отзывы с фотографиями.
4. Инструменты для брендов: страница бренда, расширенное описание.

### 8.14. Клиентские приложения

1. Адаптивная веб-витрина (mobile-first), PWA с офлайн-просмотром каталога.
2. Мобильные приложения iOS и Android (вторая очередь).
3. Telegram Mini App для покупателя и Telegram-бот для продавца (первая
   очередь — низкий порог входа на рынке Узбекистана).
4. Единый API для всех клиентов.

| Пиковая нагрузка | 5 000 запросов/с на чтение, 300 заказов/мин |
| Расчётный объём | 50 000 продавцов, 5 млн SKU, 100 000 заказов в сутки на горизонте 3 лет |
| Масштабирование | Горизонтальное для сервисов приложения; чтение каталога — через кеш и реплики |

### 9.2. Надёжность

1. Доступность ≥ 99,5 % в месяц; для платёжного и заказного контуров — ≥ 99,9 %.
2. RPO ≤ 15 минут, RTO ≤ 2 часа.
3. Резервное копирование: полное — ежесуточно, WAL/журналы — непрерывно;
   ежемесячная проверка восстановления с протоколом.
4. Отказ внешней системы (перевозчик, ОФД, ЭСФ) не блокирует оформление
   заказа: операция ставится в очередь и повторяется по стратегии backoff.
5. Все внешние вызовы — с таймаутом, повтором и «предохранителем»
   (circuit breaker).

### 9.3. Безопасность

1. HTTPS повсеместно, HSTS, современный TLS.
2. Хранение паролей — Argon2id; 2FA (TOTP) для ролей Оператора и владельцев магазинов.
3. Защита от OWASP Top 10; регулярное тестирование на проникновение перед
   каждым мажорным релизом.
4. Ограничение частоты запросов (rate limiting) и защита от перебора.
5. Платёжные данные не хранятся (PCI DSS SAQ-A), токенизация на стороне провайдера.
6. Шифрование персональных данных в покое; ключи — в защищённом хранилище.
7. Журнал аудита неизменяем (append-only), хранится не менее 5 лет.
8. Сегментация: административная панель доступна из ограниченного диапазона
   адресов либо через VPN.

### 9.4. Локализация и доступность

1. Языки интерфейса: узбекский (латиница) — основной, русский, английский.
   Архитектура допускает добавление узбекской кириллицы и каракалпакского.
2. Форматы: сум (UZS) как основная валюта, местные форматы даты, времени,
   номеров телефонов; часовой пояс Asia/Tashkent.
3. Соответствие WCAG 2.1 уровня AA для витрины: контраст, навигация с
   клавиатуры, альтернативные описания изображений.
4. Работа при медленном соединении: вес первой загрузки витрины ≤ 250 КБ
   (без изображений), «ленивая» загрузка, адаптивные изображения (WebP/AVIF).

### 9.5. SEO и трафик

1. Серверный рендеринг страниц каталога и карточек товара.
2. Человекопонятные адреса, канонические ссылки, микроразметка Schema.org
   (Product, Offer, AggregateRating, Organization), карта сайта, hreflang для
   языковых версий.
3. Отдельные посадочные страницы категорий по регионам.

### 9.6. Эксплуатационные требования

1. Развёртывание в контейнерах, конфигурация — через переменные окружения.
2. Мониторинг: метрики, журналы, трассировка запросов, оповещения дежурной смене.
3. Тестовая среда (sandbox) с эмуляторами платёжного шлюза, ОФД и перевозчиков —
   обязательна для интеграций продавцов.
4. Миграции базы данных — версионные, обратимые.

## 10. Архитектура и технологический стек

### 10.1. Принципы архитектуры

1. **Модульный монолит на старте, выделение сервисов по мере роста.**
   Преждевременное дробление на микросервисы удорожает MVP; границы модулей
   задаются сразу так, чтобы выделение было механическим.
2. Обязательно выделяются в отдельные процессы с самого начала: **платёжный
   модуль**, **поисковый индекс**, **обработчик очередей и вебхуков**.
3. Все финансовые операции — через журнал двойной записи (ledger), никакие
   суммы не пересчитываются «на лету» из заказов.
4. Событийная модель: доменные события (заказ создан, оплачен, отгружен,
   доставлен) публикуются в шину и потребляются модулями уведомлений,
   аналитики и антифрода.

## 11. Модель данных

### 11.1. Основные сущности

```
users ──< user_roles                       sellers ──< seller_users
  │                                           │
  └──< addresses                              ├──< seller_warehouses (склады ПРОДАВЦА)
                                              ├──< seller_documents (верификация)
                                              ├──< seller_payout_accounts (реквизиты расщепления)
                                              └──< seller_ratings

categories ──< category_attributes
     │
     └──< products ──< product_variants (SKU) ──< inventory_items
                │              │
                ├──< media     └──< prices ──< price_history
                └──< moderation_records

orders ──< order_items                     payments ──< payment_splits
   │                                          │
   ├──< shipments ──< shipment_events         ├──< refunds
   │        └──< carrier_labels               └──< ledger_entries (двойная запись)
   ├──< order_snapshots (версии оферты/тарифа)
   ├──< disputes ──< dispute_evidence ──< dispute_decisions
   └──< reviews ──< review_media

carriers ──< carrier_tariffs ──< delivery_zones
tariffs ──< tariff_versions ──< category_commissions
offers (оферты) ──< offer_versions ──< seller_acceptances
audit_log (append-only)
```

### 11.2. Обязательные правила

1. Все денежные значения хранятся в минимальных единицах (тийин) целым числом;
   вычисления с плавающей точкой в финансовом контуре запрещены.
2. Каждая финансовая проводка имеет парную запись в `ledger_entries`; сумма
   дебета равна сумме кредита; корректировка только сторнирующей записью.
3. `order_snapshots` фиксирует версию оферты, версию тарифа и ставку комиссии
   на момент создания заказа — их последующее изменение невозможно (принцип П4).
4. Мягкое удаление (`deleted_at`) для пользовательского контента; физическое
   удаление — только по обоснованному запросу субъекта персональных данных.
5. Мультиарендность: любой запрос к данным магазина обязательно ограничен
   `seller_id`; проверка выполняется на уровне репозитория, а не контроллера.
6. Индексы: по `seller_id`, `order.status`, `shipment.tracking_number`,
   полнотекстовые — вне основной базы, в поисковом движке.

## 12. API и внешние интеграции

1. REST (JSON) с версионированием в пути: `/api/v1/...`; допускается GraphQL

## 13. Правовые требования Республики Узбекистан

Раздел носит обязательный характер; конкретные редакции нормативных актов
уточняются юридической службой Заказчика перед вводом в эксплуатацию.

1. **Резидентство и регистрация.** Оператор — юридическое лицо, резидент РУз;
   уведомление о начале деятельности подаётся через соответствующую
   государственную платформу, сведения вносятся в государственный реестр
   субъектов электронной коммерции.
2. **Размещение данных.** Серверы и база данных, содержащие персональные
   данные граждан Республики Узбекистан, размещаются на территории Республики
   Узбекистан.
3. **Выделенные счета.** Участники электронной коммерции — юридические лица,
   индивидуальные предприниматели и самозанятые — ведут расчёты через
   выделенные банковские счета; схема расщепления настраивается с их учётом.
4. **Фискализация.** Каждой продаже соответствует фискальный чек, передаваемый
   ОФД в режиме реального времени (раздел 6.5).
5. **Защита прав потребителей.** Право на возврат товара надлежащего качества
   в установленный срок; обязательное раскрытие сведений о продавце (полное
   наименование, ИНН, адрес, контакты) в карточке товара и в чеке.
6. **Персональные данные.** Согласие субъекта, минимизация состава,
   право на удаление и на выгрузку, назначение ответственного за обработку.
7. **Реклама и маркировка.** Обязательная пометка рекламных позиций; для
   отдельных категорий — маркировка товаров и обязательная сертификация.
8. **Запрещённые к дистанционной продаже товары.** Ведётся справочник с
   автоматической блокировкой публикации.
9. **Трансграничная торговля.** При подключении иностранных продавцов —
   соблюдение таможенных и налоговых процедур, интеграция с системами
   налогового и таможенного комитетов.
10. **Хранение документов.** Договоры, оферты, чеки, решения по спорам
    хранятся не менее срока, установленного законодательством, в неизменяемом виде.

## 14. Безопасность, антифрод и модерация

### 14.1. Антифрод покупателей

Правила: скорость создания заказов с одного устройства, несовпадение
геолокации и адреса, множественные отказы от выкупа, серийные претензии,
использование множества карт с одного устройства. Реакция: усиленная
верификация, ограничение оплаты при получении, ручная проверка.

### 14.2. Антифрод продавцов

Признаки: массовая публикация карточек с чужими фотографиями, «товар-приманка»
с заниженной ценой и отменами, самовыкупы (совпадение устройств, адресов,
карт), накрутка отзывов, вывод покупателя за пределы Платформы.
Реакция: понижение в выдаче, ограничение публикации, приостановка с указанием
основания и правом апелляции. **Ручные штрафы без процедуры запрещены**
(принцип П5).

### 14.3. Модерация контента

Автоматическая проверка (запрещённые категории, стоп-слова, распознавание
изображений) + ручная проверка модератором. Срок модерации карточки — не более
24 часов. Все решения мотивированы и обжалуемы.

### 14.4. Реагирование на инциденты

Определены классы инцидентов (утечка данных, недоступность платежей, массовые
срывы доставки), ответственные, сроки уведомления Заказчика и пользователей,
порядок разбора и публикации отчёта.

## 15. Аналитика и отчётность

### 15.1. Продавцу

Продажи по дням, товарам, категориям, регионам; воронка карточки (показы →
переходы → корзина → заказ → выкуп); причины отмен и возвратов; выполнение SLA;
рейтинг с разложением по факторам; финансовый отчёт (поступления, комиссии,
возвраты, удержания); сравнение своей цены с медианой по категории (без
раскрытия данных конкретных конкурентов).

### 15.2. Оператору

Оборот (GMV), число заказов, средний чек, активные продавцы и покупатели,
удержание пользователей (retention), доля отменённых заказов, доля споров и
их исход, срок доставки по регионам, доля региональных продавцов, доходы по
источникам, стоимость привлечения.

### 15.3. Публичная отчётность (элемент доверия)

Ежеквартально публикуются: медианный срок поступления денег продавцу, доля
заказов, доставленных в срок, доля споров и распределение решений, число
приостановленных аккаунтов с разбивкой по основаниям. Публикация обязательна —
она является частью ценностного предложения Платформы.

### 15.4. Требования к реализации

Данные для аналитики читаются из отдельного хранилища (реплика или витрина),
чтобы не нагружать транзакционный контур; глубина хранения — не менее 3 лет;
выгрузка в CSV/XLSX и через API.

## 17. Порядок приёмки и тестирование

### 17.2. Критерии приёмки MVP (обязательные)

| № | Критерий |
|---|---|
| 1 | Продавец регистрируется, проходит проверку по государственному реестру и публикует товар без участия поддержки |
| 2 | Покупатель оформляет заказ из товаров двух разных продавцов одним платежом |
| 3 | Платёж расщепляется: доля продавца зачисляется на его расчётный счёт, комиссия — Оператору; операция подтверждается реестром провайдера |
| 4 | В защищённом режиме деньги раскрываются продавцу автоматически в течение 24 ч после подтверждения получения |
| 5 | Продавец создаёт отправление у перевозчика в один клик, печатает накладную, покупатель видит трекинг |
| 6 | Возврат исполняется тем же методом оплаты, комиссия Оператора возвращается пропорционально |
| 7 | Спор проходит все шаги процедуры и завершается мотивированным решением в срок ≤ 5 рабочих дней |
| 8 | Отзыв невозможно оставить без доставленного заказа и невозможно удалить продавцом |
| 9 | В системе отсутствует возможность создать склад Оператора или учётную запись продавца, аффилированную с Оператором |
| 10 | Изменение тарифа не влияет на ранее созданные заказы; в заказе сохранена версия тарифа |
| 11 | Продавец выгружает полный набор своих данных одной операцией |

### 17.3. Гарантийные обязательства

Гарантийный срок — 12 месяцев с даты подписания акта ввода в эксплуатацию.
Критические дефекты (недоступность, потеря или неверное распределение денежных

## 18. Риски и меры их снижения

| Риск | Последствие | Мера снижения |
|---|---|---|
| Платёжный провайдер не поддерживает расщепление в нужном виде | Невозможна ключевая идея Платформы | Проработка на этапе 0 до начала разработки; договор не менее чем с двумя провайдерами; резервная схема — субсчета мерчантов |
| Регуляторные ограничения на движение средств | Задержка запуска | Юридическое заключение до этапа 1; согласование схемы с банком-партнёром и регулятором |
| Продавцы срывают сроки отгрузки | Падение доверия покупателей | Жёсткие SLA с автоматическим влиянием на выдачу, обучение продавцов, «Проверенный продавец», страховка срока доставки |
| Неравномерное качество упаковки | Рост споров | Обязательная фиксация вложения, стандарты упаковки, партнёрская поставка упаковочных материалов |
| Недостаток продавцов на старте («холодный старт») | Пустой каталог | Пилот в двух регионах с точечным подключением производителей; нулевая комиссия первые 3 месяца; перенос каталога из существующих площадок импортом |
| Потребительский фрод при возвратах | Убытки продавцов | Состязательная процедура, доказательства, профилирование покупателей |
| Демпинг и недобросовестная конкуренция | Деградация качества | Прозрачное ранжирование по сроку доставки и рейтингу, а не только по цене |
| Логистика в отдалённых районах | Недоступность сервиса | Мультиперевозчик, почта, самовывоз, локальные партнёры |
| Зависимость от одного перевозчика | Остановка доставок | Не менее трёх подключённых перевозчиков, автоматическое переключение |
| Утечка персональных данных | Юридические и репутационные последствия | Шифрование, минимизация, аудит, тестирование на проникновение, план реагирования |

### 19.2. Статусная модель

**Заказ:** `created` → `awaiting_payment` → `paid` → `in_progress` →
`partially_shipped` → `shipped` → `delivered` → `completed`.
Побочные ветви: `cancelled` (до отгрузки), `refunded`, `partially_refunded`,
`disputed`.

**Отправление:** `new` → `confirmed` → `packed` → `handed_to_carrier` →
`in_transit` → `arrived` → `out_for_delivery` → `delivered` → `closed`.
Побочные ветви: `cancelled`, `return_initiated`, `returning`, `returned`, `lost`.

**Платёж:** `initiated` → `authorized` → `captured` → `split_pending` →
`split_done` → `settled`. Побочные ветви: `failed`, `refund_pending`,
`refunded`, `partially_refunded`, `chargeback`.

**Спор:** `opened` → `seller_response` → `arbitration` → `decided` →
`executed` → `closed`. Побочная ветвь: `appealed` → `arbitration`.

**Продавец:** `draft` → `pending` → `active` → `limited` → `suspended` →
`terminated`.
